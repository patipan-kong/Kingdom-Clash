# Temporary Assets and Known Limitations - Phase 1A

- All generated world art, ability icons and six polished HUD icons were created with the built-in image generation tool. No externally downloaded game/UI artwork or licensed character likenesses are used. All ten prompts and source filenames are recorded in `art/prompts.json`. The earlier referenced screenshot was not available in the received context; that refinement used the written camera/control requirements, without claiming an exact screenshot match.
- Units and structures use single-pose PNGs. Minion idle bobbing, contact shadows, selection rings and skill rings are procedural presentation effects. There are no walking, attacking, damage or directional animation sheets. The Guardian plume reaches the top edge of its generated source.
- Guardian/enemy HP, combat, movement, spawning, death, respawn and Gold rewards are real simulation state. XP/levels, Wood/Iron, blue minions and structures remain staged. No full economy, skills, construction, objectives, win/loss, progression, save system or APK is implemented. See [Phase 1A](PHASE_1A.md) for balance assumptions and review steps.
- Guardian movement now uses fixed simulation time and swept radius collision against water, bridge, structures, scenery and boundaries. Enemy minions use direct steering and a fixed bridge waypoint. There is no unit separation, dynamic pathfinding, wall breaching or obstacle route search; minions can stop at arbitrary obstacles.
- Grid shows logical footprints for review, not build mode. Tower/wall footprints follow the specification. A base footprint of 3 × 3 is an explicit prototype assumption. Sprites may extend outside their footprint.
- The minimap observes actual Guardian/enemy positions and removes defeated enemies. It retains camera survey behavior. Build/Shop/Army panels remain illustrative; Build/Shop apply absolute 0.25 simulation speed while open. Skill rings, basic attack rings and damage text are temporary visual effects.
- The original painted background is archived outside the build. The scene uses repeatable grass/path/water textures, shared lane/river/bridge geometry and independent props. Texture repetitions, straight lane/river bounds and procedural shoulder/shore accents remain visible. This is a compact modular prototype, not an autotile editor or finished environment library. Perspective/light alignment and transition art still need a production artist pass.
- Canvas uses FIT with a fixed 960 × 540 camera viewport over the larger projected world. Wider displays have side bars instead of expanding world view. This remains a visual-review simplification of spec 06. Bottom controls adapt to measured canvas scale: 48 CSS pixel minimum skill/utility targets and 68-pixel minimum Attack, checked down to 568 × 320. Utilities use smaller visible art over larger invisible circular targets. Their column spreads vertically on short screens; physical right-thumb reach is not yet assessed. A 24 CSS pixel bottom strip supplements safe-area insets but cannot guarantee behavior across Android gesture implementations. Unchanged top HUD text and portrait/Pause targets become small on 320-pixel-tall screens (about 40 CSS pixel portrait/Pause targets); these approved elements were preserved as requested. Very short screens below the verified range need a collapsible utility tray review. World-edge camera clamping naturally moves the hero away from screen center.
- Desktop Chrome WebGL rendering is verified, including emulated viewport/touch checks. No physical Android/iOS device, Android WebView, APK, frame-time benchmark, Canvas fallback, screen-reader workflow or real device multi-finger interaction has been verified. No audio is included.
- Phaser is bundled locally, producing a relatively large JavaScript chunk. Vite reports a chunk-size advisory; code splitting and device performance profiling are later work.

Phase 1A is complete at this scope and stops for review. Subsequent slices are not implemented.
